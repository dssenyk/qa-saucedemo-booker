## Де агент помилився

### 1. Негативний пароль не проходив у тип

`booker` у конфігу оголошений через `as const`. Сигнатура вийшла такою:

```ts
authenticate(username = booker.username, password = booker.password)
```

TypeScript звузив `password` до літерала `"password123"`. Виклик `authenticate('admin', 'wrong-password')` у негативному тесті став помилкою компіляції `TS2345`, ще до браузера.

Помітив по виводу `npx tsc --noEmit`. Параметри тепер явно `string`. Без цього «негативний логін» фізично не зібрався б, і агент міг би підставити в тест той самий правильний пароль.

### 2. «Add to cart» шукався як будь-яка кнопка

На картці товару три елементи з роллю button: посилання на фото, посилання на назву (обидва «View details for …») і справжній `<button>Add to cart`. Асерт `getByRole('button')` усередині картки впав із strict mode violation і перелічив усі три. Третім у списку був уже `remove-sauce-labs-backpack` з текстом Remove, тобто клік додавання встиг спрацювати, зламалась лише перевірка.

Помітив по тексту помилки Playwright: вона показала якір `item-4-img-link`, якір `item-4-title-link` і кнопку Remove. Виправлення: `locator('button')`, він не чіпає `<a role="button">`. Те саме правило записане в `AGENTS.md`.

### 3. Назву товару звірив з усім каталогом, який лишився в DOM

`openProduct` клікав назву, чекав URL `inventory-item.html?id=…` і одразу робив `getByTestId('inventory-item-name')`. URL вже був карткою товару, але локатор бачив шість імен. Агент майже записав це як баг «картка не відкривається»: ранній скрипт прочитав DOM у той самий тік, коли змінився URL, і теж побачив увесь каталог.

Помітив, зіставивши дві речі. Снапшот падіння вже показував кнопку Back to products і один рюкзак. Повторний скрипт із очікуванням цієї кнопки показав одну назву, одну ціну і `back-to-products`. Каталог не зникає з DOM, він просто невидимий. Тест тепер спершу чекає Back to products і читає лише `filter({ visible: true })`.

### 4. Logout шукався як посилання, меню — за неіснуючим кліком

Перша версія клікала `data-test="open-menu"`. Кнопки з таким атрибутом, яка приймає клік, на сторінці немає: доступне ім'я кнопки — Open Menu. Після виправлення меню відкрилось, і тест 30 секунд чекав `getByRole('link', { name: 'Logout' })`.

Помітив по call log `waiting for getByRole('link', { name: 'Logout' })` і по скріншоту: дровер уже відкритий, пункт Logout на екрані. У accessibility snapshot цей пункт має роль button (`<a>` з `role="button"` або кнопка), About поруч справді link. Клік по `getByRole('button', { name: 'Logout' })` завершив вихід за 1.7 с.

### 5. Чужий контекст і статус 201 ледь стали чужими багами

Дві різні помилки висновку, обидві спіймані до того, як потрапили в README.

**201 на видалення.** Живий `DELETE` успішного бронювання повернув `201 Created`. Перша реакція була записати це як дефект семантики REST (очікував 204). Перш ніж нести це в баг-репорт, звірив приклад DeleteBooking в apidoc: там прямо `HTTP/1.1 201 Created`. Це контракт стенда, не розбіжність. У життєвому циклі тест очікує 201, а що запису немає, доводить наступний `GET` зі статусом 404. Те саме з `GET /ping`: у документації теж 201, в набір він не входив.

**Порожній каталог `error_user`.** Перший скрипт робив `browser.newPage()` в тому самому context після логіну `standard_user`. Наступний логін успадкував сесію: каталог виглядав порожнім, а кошик уже містив усі товари, причому логи кліків не надрукувались. Це не збігалося з чистим входом. Повтор у `browser.newContext()` показав шість товарів і справжній дефект: три кнопки лишаються Add to cart, бейдж показує 3, у кошику 6 позицій. У README потрапив другий результат (BUG-UI-3), не перший.

Помітив обидва рази не «на око», а порівнянням: статус видалення зі сторінкою apidoc, а дивний кошик `error_user` з прогоном у чистому context.
